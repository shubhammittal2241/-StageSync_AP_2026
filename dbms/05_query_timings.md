# StageSync: Query Execution Plans & Performance Benchmark

This document analyzes the execution plans, planning times, and runtime performance of key SQL queries in StageSync. All queries were executed against PostgreSQL on the normalized 23-table relational schema (`stagesync`) with realistic production-scale test data.

The raw query plans generated by `EXPLAIN (ANALYZE, BUFFERS, VERBOSE)` are stored in the `./plans/` directory.

## 3. Detailed Query Analysis & Execution Plans

### Query 1: Artist Filter by Location, Experience, and Genre
- **Raw Plan File:** [`./plans/q1_artist_search.txt`](./plans/q1_artist_search.txt)
- **Purpose:** Fast artist lookup when an event planner searches by city, minimum years of experience, and musical genre.

```sql
SELECT ap.id, ap.stage_name, ap.professional_type, ap.experience_years, ap.hourly_rate, g.name AS genre_name
FROM artist_profiles ap
JOIN artist_genres ag ON ap.id = ag.artist_id
JOIN genres g ON ag.genre_id = g.id
WHERE ap.city = 'Mumbai'
  AND ap.experience_years >= 5
ORDER BY ap.hourly_rate ASC;
```

- **Execution Analysis:**
  - The query planner utilizes `idx_artist_profiles_city` to reduce candidate rows down to 4 matching profiles.
  - Candidate IDs are joined with the junction table `artist_genres` using a Bitmap Index Scan on `artist_genres_pkey`.
  - Finally, genre names are fetched via an Index Scan on `genres_pkey`.
  - **Planning Time:** 2.997 ms | **Execution Time:** 0.217 ms | **Shared Buffer Hits:** 19
  - **Viva Note:** Because city filtering is selective, indexing `city` avoids a full sequential scan across the table.

### Query 2: Artist Schedule Conflict Detection (Algorithm B)
- **Raw Plan File:** [`./plans/q2_booking_conflict.txt`](./plans/q2_booking_conflict.txt)
- **Purpose:** Core concurrency check to prevent double-booking an artist across overlapping time windows.

```sql
SELECT id, artist_id, start_time, end_time, status
FROM bookings
WHERE artist_id = '22222222-2222-2222-2222-222222222205'
  AND status NOT IN ('CANCELLED')
  AND start_time < '2026-11-20 23:00:00+05:30'
  AND end_time > '2026-11-20 18:00:00+05:30';
```

- **Execution Analysis:**
  - PostgreSQL chooses an Index Scan using the GiST exclusion index `no_artist_booking_overlap`.
  - The range overlap operator evaluates boundary conditions directly within the index leaf pages.
  - **Planning Time:** 4.590 ms | **Execution Time:** 10.162 ms | **Shared Buffer Hits:** 42
  - **Viva Note:** This query mirrors the database-level GiST exclusion constraint. Even under high concurrency, the index scan identifies overlaps without table-level locking.

### Query 3: Setlist Duration & Target Gap (Algorithm C)
- **Raw Plan File:** [`./plans/q3_setlist_duration.txt`](./plans/q3_setlist_duration.txt)
- **Purpose:** Computes the total duration of all planned songs in a setlist and compares it against the event's target duration to identify gaps or overruns.

```sql
SELECT sl.id, sl.name, sl.target_duration_seconds,
       COALESCE(SUM(s.duration_seconds), 0) AS total_song_seconds,
       sl.target_duration_seconds - COALESCE(SUM(s.duration_seconds), 0) AS remaining_seconds
FROM setlists sl
LEFT JOIN setlist_songs ss ON sl.id = ss.setlist_id
LEFT JOIN songs s ON ss.song_id = s.id
WHERE sl.id = 'cccccccc-cccc-cccc-cccc-ccccccccccc1'
GROUP BY sl.id, sl.name, sl.target_duration_seconds;
```

- **Execution Analysis:**
  - Evaluated using a `GroupAggregate` over an Index Scan on `setlists_pkey` joined to `setlist_songs` and `songs`.
  - Hash join handles the song duration lookup in single-pass memory.
  - **Planning Time:** 3.607 ms | **Execution Time:** 0.715 ms | **Shared Buffer Hits:** 5
  - **Viva Note:** Aggregation is performed in-memory on only 5 buffer hits because the primary key lookup pinpoints the specific setlist record immediately.

### Query 4: Stage Equipment Availability & Conflict Check (Algorithm E)
- **Raw Plan File:** [`./plans/q4_equipment_availability.txt`](./plans/q4_equipment_availability.txt)
- **Purpose:** Ensures stage equipment (microphones, amplifiers, mixing consoles) is not assigned to two different events at the same time.

```sql
SELECT e.id, e.name, e.category, e.daily_rate
FROM equipment e
WHERE e.category = 'Audio'
  AND e.operational_status = 'AVAILABLE'
  AND NOT EXISTS (
      SELECT 1 FROM equipment_reservations er
      WHERE er.equipment_id = e.id
        AND er.status IN ('CONFIRMED', 'IN_USE')
        AND er.start_time < '2026-11-20 23:00:00+05:30'
        AND er.end_time > '2026-11-20 18:00:00+05:30'
  );
```

- **Execution Analysis:**
  - The query planner transforms the `NOT EXISTS` subquery into a `Hash Anti Join`.
  - The index on `equipment(operational_status, category)` filters available hardware, while active reservations are probed in hash memory.
  - **Planning Time:** 2.323 ms | **Execution Time:** 0.162 ms | **Shared Buffer Hits:** 8
  - **Viva Note:** The Anti Join optimization allows PostgreSQL to discard reserved equipment in $O(1)$ time per candidate without nested row-by-row iteration.

### Query 5: Event Financial & Attendance Summary View
- **Raw Plan File:** [`./plans/q5_event_summary_view.txt`](./plans/q5_event_summary_view.txt)
- **Purpose:** Comprehensive event dashboard calculating total artist payouts, equipment expenses, and attendee headcount.

```sql
SELECT e.id, e.title, e.event_type, e.status, v.name AS venue_name,
       COUNT(DISTINCT b.id) AS total_artists_booked,
       COALESCE(SUM(b.fee), 0) AS total_artist_payout,
       COUNT(DISTINCT er.id) AS total_equipment_items,
       COALESCE(SUM(er.fee), 0) AS total_equipment_cost
FROM events e
LEFT JOIN venues v ON e.venue_id = v.id
LEFT JOIN bookings b ON e.id = b.event_id AND b.status = 'CONFIRMED'
LEFT JOIN equipment_reservations er ON e.id = er.event_id AND er.status = 'CONFIRMED'
GROUP BY e.id, e.title, e.event_type, e.status, v.name;
```

- **Execution Analysis:**
  - Executed via `Hash Left Join` and `HashAggregate`.
  - Aggregations are calculated over filtered relation sets without duplicate cartesian growth.
  - **Planning Time:** 3.868 ms | **Execution Time:** 0.421 ms | **Shared Buffer Hits:** 8
  - **Viva Note:** Demonstrates complex multi-table joins (events, venues, bookings, reservations) returning aggregated production costs in under 0.5 ms.

### Query 6: Artist Career Earnings & Settlement Ratio
- **Raw Plan File:** [`./plans/q6_artist_career_earnings.txt`](./plans/q6_artist_career_earnings.txt)
- **Purpose:** Generates financial statements for artists, tracking contracted fees, paid amounts, and outstanding balance.

```sql
SELECT ap.stage_name,
       COUNT(b.id) AS total_gigs,
       COALESCE(SUM(b.fee), 0) AS contracted_earnings,
       COALESCE(SUM(p.amount), 0) AS total_received,
       COALESCE(SUM(b.fee), 0) - COALESCE(SUM(p.amount), 0) AS pending_settlement
FROM artist_profiles ap
JOIN bookings b ON ap.id = b.artist_id
LEFT JOIN payments p ON b.id = p.booking_id AND p.status = 'COMPLETED'
GROUP BY ap.id, ap.stage_name
ORDER BY contracted_earnings DESC;
```

- **Execution Analysis:**
  - Uses `idx_payments_booking_id` for payment resolution linked to each confirmed booking.
  - Result grouped by HashAggregate and sorted.
  - **Planning Time:** 2.957 ms | **Execution Time:** 2.846 ms | **Shared Buffer Hits:** 6
  - **Viva Note:** Demonstrates accurate handling of outer joins for bookings where payments have not yet settled.

### Query 7: Band Lineup & Active Member Instrumentation
- **Raw Plan File:** [`./plans/q7_band_lineup.txt`](./plans/q7_band_lineup.txt)
- **Purpose:** Pulls band member roster, stage role (Lead Vocals, Bass, Drums), and primary instrument.

```sql
SELECT b.name AS band_name, bm.role, ap.stage_name, i.name AS instrument
FROM bands b
JOIN band_members bm ON b.id = bm.band_id AND bm.is_active = TRUE
JOIN artist_profiles ap ON bm.artist_id = ap.id
LEFT JOIN instruments i ON bm.instrument_id = i.id
WHERE b.id = '33333333-3333-3333-3333-333333333301';
```

- **Execution Analysis:**
  - Utilizes composite index `idx_band_members_band_active` (`band_id`, `is_active`).
  - Left join with `instruments` resolves optional instrument assignments without dropping vocalists or producers.
  - **Planning Time:** 2.954 ms | **Execution Time:** 0.130 ms | **Shared Buffer Hits:** 18
  - **Viva Note:** Single fastest join traversal in the system (0.130 ms) due to the composite partial index on active members.

### Query 8: Cumulative Event Budget Allocation (Window Function)
- **Raw Plan File:** [`./plans/q8_running_budget.txt`](./plans/q8_running_budget.txt)
- **Purpose:** Financial timeline tracking cumulative spending across an organizer's consecutive events.

```sql
SELECT organizer_id, title, start_time, budget,
       SUM(budget) OVER (
           PARTITION BY organizer_id
           ORDER BY start_time
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS cumulative_budget
FROM events;
```

- **Execution Analysis:**
  - PostgreSQL uses a `WindowAgg` node preceded by an in-memory quicksort (`Memory: 25kB`).
  - Zero disk spill; window frame computed in a single sequential pass.
  - **Planning Time:** 1.096 ms | **Execution Time:** 0.496 ms | **Shared Buffer Hits:** 7
  - **Viva Note:** Demonstrates standard SQL analytic functions (`OVER (PARTITION BY ... ORDER BY ...)`).

## 4. Key Indexing & Query Optimization Insights

1. **GiST Exclusion Constraints vs. Application Checking:**
   - Traditional applications run multiple `SELECT` queries and rely on application-level locks to check booking conflicts, which allows race conditions.
   - StageSync enforces `no_artist_booking_overlap` and `no_venue_booking_overlap` directly in the database engine via GiST indices with range types (`tsrange`), making race conditions mathematically impossible.

2. **Index Selectivity:**
   - Indices on high-cardinality foreign keys (`event_id`, `artist_id`, `venue_id`) consistently yield single-digit millisecond query execution times.
   - Partial composite indices (`idx_band_members_band_active`) filter out historical/inactive records at the index level, minimizing buffer hits.

3. **In-Memory Sorts and Joins:**
   - All sorting operations and hash joins execute in work memory (`work_mem`), avoiding temporary files on disk.
